# 第一步：不可变字节键

本步交付 `ByteKey` 和对应测试。它为未来 TreeMap、跳表与磁盘索引建立共同的键语义。当前类型位于 `model` 包，后续实现见 [MemTable 学习笔记](memtable.md)。

## 为什么不能直接使用 byte[]

数组默认按对象身份判断相等，两个内容相同的数组仍可能被当成不同键；数组也没有我们需要的自然顺序。更重要的是，数组可被调用方修改。如果键在放入树后发生变化，它的位置可能不再符合排序规则；如果放入哈希表后哈希值变化，查找也可能失败。

## 从代码看三个约束

### 1. 内容由 ByteKey 独立持有

`copyOf` 经私有构造方法复制输入数组，`toByteArray` 复制输出数组。`private final` 固定字段引用，`clone()` 才隔离外部对内容的修改。类声明为 `final`，避免子类覆盖相等或比较方法而破坏约定。

```java
byte[] input = {1, 2};
ByteKey key = ByteKey.copyOf(input);
input[0] = 9;
byte[] output = key.toByteArray();
output[1] = 8;
// key 仍为 [1, 2]
```

### 2. 内容相等与比较结果一致

`equals` 使用 `Arrays.equals`，`hashCode` 使用 `Arrays.hashCode`。比较结果为零当且仅当内容相等。TreeMap 依赖比较结果判定同一个键；HashMap 依赖 hashCode 与 equals。这种一致性让不同索引对“同一个键”的理解一致。

相等键必须有相同哈希；不同键可以发生哈希碰撞，测试不能反过来要求所有不同键的哈希都不同。

### 3. 统一使用无符号字节字典序

`compareTo` 调用 `Arrays.compareUnsigned`，从左向右找首个不同字节，以 0 至 255 比较；共同前缀相同时短键在前。返回值只应判断正、负、零，不能假定恰好返回 -1 或 1。

以下均为十六进制：

```text
[] < [00] < [01] < [01, 00] < [01, FF] < [02] < [7F] < [80] < [FF]
```

Java 的 `(byte) 0x80` 数值为 -128，但我们的排序将其视为 128，因此位于 0x7F（127）之后。空数组是合法键，null 是非法输入；这与后续“键未找到”无关。

文本与数字如何编码是上层问题。例如 UTF-8 文本 "10" 排在 "2" 前；如需数字顺序，应选择保序编码。

## 验证与取舍

`ByteKeyTest` 用 10 个测试覆盖输入/输出修改隔离、空与 null、内容相等、前缀排序、全部 256 个单字节值的两两比较、样本上的比较一致性/反对称性/传递性，以及 TreeMap 同键覆盖和 HashMap 查找。性质测试是对所选样本的验证，不是任意长度输入的形式化证明。

防御性复制带来 O(n) 拷贝和内存分配；比较最坏需要 O(n) 扫描，哈希也按内容计算。首版选择明确的数据所有权，暂不增加零拷贝接口或哈希缓存。未来优化须保持这些可观察行为。

```sh
./mvnw -Dtest=ByteKeyTest test
./mvnw clean verify
```
