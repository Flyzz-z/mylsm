# Compaction 阶段复盘

本阶段完成 SSTable 可暂停游标、多路有序归并、Manifest 全量替换，以及唯一后台线程上的自动阈值触发与同步手动 compact()。每次把任务开始时全部已发布表归并为一张，保留每键最新 Value 或 Tombstone；前台仍串行调用。

## 从记录归并到文件集提交

假设 Manifest 按旧到新引用 `[3,5]`，压缩预留输出编号 6：

```text
持锁固定输入 [3,5] 及顺序，预留输出 6
  → 锁外打开独立 Reader，逐块归并并写出、同步、关闭 6.sst
  → 关闭独立输入，打开完整输出
  → 持锁基于最新 Manifest 提交 SST=[6]，安装新读取集
  → 关闭旧前台 Reader，再尝试删除 3.sst、5.sst
```

构建期间前台可以轮换 WAL，例如从 active=4 变为 active=7、frozen=4。发布必须沿用最新的 active=7、frozen=4 及封存长度，只替换固定的 SST 输入集；后续 flush 再发布为 `[6,8]`。因此输出编号 6 小于新 WAL 编号 7 是合法的，文件编号不表示记录版本。

Manifest 的提交是有效文件集切换边界。输出文件存在、构建结束或编号较大，都不能替代提交；同步报错也不等于提交必定回滚。当前实例停止服务并保留可能有效的文件，重启按最后完整有效状态恢复。

## 归并正确性与成本

最小堆每路保存一个 Source，包含当前记录、游标及输入位置 generation。堆按 ByteKey 的无符号字节字典序比较；同键出堆顺序不表示新旧，必须显式选择 generation 最大的记录。generation 就是本次输入在 Manifest 清单中的位置，不写入记录，也不是 MVCC 版本。

每次取最小键，排空所有同键头，选最新记录，并推进参与输入；推进后的头重新入堆。同键组全部成功后才暴露结果，任何读取损坏都不能当作耗尽。头记录改变前必须先出堆，否则 PriorityQueue 不会自动恢复排序。

游标创建时不读取数据块，next() 才按需读块；一个 Reader 同时只允许一个游标，耗尽仍须显式关闭。后台使用独立 Reader，避免与前台点查争用单线程读取状态。Reader 索引常驻内存，游标保存当前已验证块，记录内容按需从磁盘读取。

N 条输入、K 张表的归并约为 O(N log K)；堆与 Source 为 O(K)，记录缓冲包括 K 个输入块及输出块，Reader 索引另计。没有把全库记录收集进 Map，也不能把流式读取说成恒定内存。

最新 Tombstone 保留，包括删除一个从未存在的键。get 区分 Value、Tombstone 和缺失：即使本次全量压缩覆盖全部旧 SST，丢弃 Tombstone 仍会改变公开接口的三态结果。

## 后台执行、同步返回与锁边界

| 边界 | 已实现行为与理由 |
| --- | --- |
| 自动触发 | 有效表数达到阈值时执行，默认 4、至少 2；恢复及任务发布后重查，不增加检测线程或定时轮询 |
| 工作顺序 | 同一 worker 在任务边界按 frozen flush → 手动请求 → 自动压缩选择；已开始任务执行到底 |
| 同步 compact() | 先 flush 调用前的内存数据，再登记请求并等待 done/error；少于两张表无操作 |
| 通知与完成 | Condition 负责唤醒，while 重查共享状态；取走请求或 Manifest 发布均不等于整个请求完成 |
| 中断 | 保留标志并报 InterruptedIOException，不取消已提交任务；再次调用先等待旧请求释放槽位 |
| 锁边界 | 固定输入、编号和发布持锁，耗时归并在锁外；等待原子释放锁，前台 WAL 状态可能在期间更新 |
| 关闭 | 拒绝新任务，未开始的手动请求明确失败，已开始任务结束后才释放资源；active 可由 WAL 恢复 |
| 回收失败 | 旧 Reader 关闭失败报告后台错误；旧文件删除失败只留孤儿，不撤销有效发布 |

唯一后台线程保证 SST 发布不并行，锁还需协调前台 WAL 轮换、读取集及生命周期；不能因为只有一个 worker 就省去固定输入和发布时的锁。前台 get 全程持锁且不泄露 Reader，因此安装后可以关闭旧 Reader，当前无需通用 Version 引用计数。

## 用户讨论与方案选择

- 用户明确以学习理解为主，要求先讨论原理，再确定压缩设计，逐步实现各部分。
- 围绕“检测是否由调用线程完成”“后台结果返回给谁”和“compact 是否同步”，最终选择唯一后台线程，自动阈值与同步手动入口并存。用 Condition 和共享请求状态实现通知，没有新增 chan、任务队列或轮询线程。
- 用户询问 cursor 的 next block 赋值及内存/磁盘状态划分；游标从初始块位置推进，索引常驻、数据块按需读取，输入间各自维护进度。
- 用户追问堆保存的记录如何比较，以及锁是否只在最后获取；实现明确区分按键选取与同键代际选择，并在任务开始和发布两个边界持锁。
- 用户询问 generation 来源、记录是否有版本，以及 MVCC 是否需要记录版本；本阶段只使用输入顺序选择最新值，MVCC 涉及记录版本及可见性设计，留在未来另行讨论。
- 自动触发完成后，用户继续要求实现手动接口，并在其完成后指示“阶段复盘归档”；本次整理既有讨论和验收结果，不扩展下一阶段。

## 验收证据与保留的取舍

本阶段最终实现已通过 `./mvnw test` 和 `./mvnw clean verify`：619 个测试，0 失败、0 错误。覆盖逐块游标、多路重复键与删除、受限 Manifest 转换、自动阈值、锁外读写及 WAL 轮换、背压与 flush 优先、手动等待/中断/关闭，以及构建、提交和资源清理故障。

其中 4 个压缩独立 JVM 用例在部分输出、完整输出未提交、提交后、旧输入部分回收后通过 Runtime.halt 退出，核对原始文件集、两份 WAL、三态读取及恢复后续写。它们验证进程退出模型，不替代断电验证。

全量单输出便于理解与验证，但写放大较高，输入输出需要临时共存，持续 flush 也可能推迟压缩。单输出仍受既有 64 MiB 索引载荷上限限制，超限明确失败，不自动拆表。记录无 MVCC 版本，不支持快照、分层策略、部分输入压缩或 Tombstone 回收；Manifest 追加历史尚未回收。沿用现有帧结构，但旧二进制不识别压缩转换，不能回退打开已压缩数据库。
