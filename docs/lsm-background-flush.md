# 单冻结表与后台刷盘

LsmStore 按逻辑字节目标轮换 WAL、冻结内存表，并由唯一后台线程构建和发布 SSTable。恢复时若 Manifest 引用冻结 WAL，也会重新启动同一刷盘流程。后续已补充显式 flush；启动时的内部孤儿清理和完整阶段验收仍待完成。

## 前台与后台如何分工

接口新增 `open(Path, long memTableTargetBytes)`，阈值必须为正，默认重载使用 4 MiB。阈值按每键最新编码记录的总字节量计算，不是堆内存上限，也不是 WAL 历史长度上限。

一个 ReentrantLock 串行化状态、两代 MemTable、WAL 写入、Manifest 提交及共享 SSTable Reader 的访问。前台仍要求串行调用；内部一个工作线程长期等待 Condition，没有无界任务队列或每次轮换新建线程。

| 操作 | 是否持状态锁 |
| --- | --- |
| 参数/容量协调、WAL 追加同步、内存应用 | 是 |
| 准备新 WAL、封存旧 WAL、提交轮换状态 | 是 |
| 为冻结表取得有序快照、分配输出编号 | 是 |
| 构建 SSTable、打开尚未共享的输出 Reader | 否 |
| 准备并提交发布状态、安装 Reader、移除冻结表 | 是 |
| 删除已无引用的旧 WAL | 否 |
| 等待冻结槽位或后台线程退出 | 等待期间不持锁 |

后台从冻结表复制一份有序快照引用列表，再惰性适配为 SsTableRecord，不另收集全表记录。取快照会短暂占锁；文件构建的耗时不占锁。快照、块缓冲、索引和对象都有额外内存，不能用两张表的逻辑阈值推导精确堆上限。

## 阈值与背压

合法参数在等待和轮换前验证。若当前活跃表已达到目标：

- 有冻结表：Condition.await 释放锁等待，醒来后重查状态与槽位。
- 没有冻结表：先轮换，再接受本次写入。

当前操作完整追加同步后才应用到内存。如果活跃表刚达到目标且槽位空闲，返回前执行轮换并唤醒后台；若槽位忙，先保留已满活跃表，下一条写入再等待。覆盖和删除不绕过这个规则。

允许一条合法大记录使表跨过目标，一条记录不拆分。比如目标 11 字节，第一条 a=1 形成冻结表；后台暂停时 b=2 仍可写入新活跃表，下一条 c=3 必须等前一代发布，在等待前不能追加 c 的 WAL。

## 两次提交分别保证什么

轮换持锁依次执行：准备并同步新 WAL → 关闭旧 writer 并获取封存长度 → 提交同时引用两代 WAL 的 Manifest → 切换活跃表/writer 并设置冻结表 → 唤醒工作线程。新 WAL 在提交为 active 之前不接纳用户数据。

后台锁外写完 SSTable 并打开 Reader 后，重新取锁，从当前 Manifest 构造新状态：保留当前活跃 WAL，追加 SSTable，清除 frozen 引用。Reader 清单和资源清单都在提交前准备，提交成功后只做引用安装、清除冻结槽位并唤醒等待者。随后才在锁外尝试删除旧 WAL。

```text
初始：active=1，frozen=无，sst=[]
轮换：active=2，frozen=1，sst=[]
发布：active=2，frozen=无，sst=[3]
```

前台查询一直遵守 active → frozen → SSTable 从新到旧的顺序，因此冻结代变成 SSTable 后，其逻辑年龄不变；新活跃表中的值或删除仍遮蔽它。

工作线程发布时不使用提前保存的整份文件集覆盖当前状态。若前台已经因读取或写入错误将实例判为 FAILED，后台不再提交新状态，关闭尚未移交的输出 Reader，并保留 WAL 恢复来源。

## 失败与等待者

轮换中的新建、旧 WAL 关闭/取长度、Manifest 提交失败均使实例 FAILED。当前 put 可能已经写入并同步旧 WAL，因此失败结果仍不确定，不能承诺这条记录恢复后不存在。新旧文件保留供恢复判断。

后台构建、打开输出、发布或工作线程内部失败会保存原因、进入 FAILED 并 signalAll。已在等待槽位的写入得到带原始原因的 IOException，尚未追加的操作不出现于日志；之后新调用被状态检查拒绝。未发布输出即使完整存在也只是孤儿，不参与恢复。

后台错误也会通过 close 报告，避免没有后续请求时错误无人观察。若发布成功但旧 WAL 删除失败，仅留下无引用文件，不撤销发布，也不把它恢复为有效日志。线程创建/启动失败在 open 阶段释放已取得资源，不暴露半个实例。

前台条件等待被中断时，恢复中断标志并抛 InterruptedIOException，不因调用方中断丢弃冻结数据或将正常服务判坏。本次等待发生在 WAL 追加之前。

## close 必须与本步一起协调

引入后台线程后，不能继续使用“直接关闭全部文件”的旧实现。close 进入 CLOSING 并唤醒工作线程；若已有冻结任务，允许它完成发布，否则空闲线程退出。调用方在锁外 join，工作线程结束后才关闭共享资源并置 CLOSED。发生错误也继续清理，关闭后不可恢复服务，重复关闭安全。

关闭等待不因调用线程中断提前释放文件资源，等待及清理完成后恢复标志。剩余活跃表不额外冻结，重启仍可从 active WAL 恢复。此关闭协调是接线程的必要前置工作，因此随后台刷盘完成原任务 6.3。

## 显式 flush 的等待边界

`flush()` 已提供主动刷盘：前台仍串行调用，成功返回时调用前的内存记录都已成为 Manifest 中的有效 SSTable。流程复用 rotate 和后台发布，不另建写文件路径或新线程：

```text
持锁检查 OPEN
    → 若已有 frozen，释放锁等待它发布，醒来重查
    → 若 active 非空，轮换 WAL，唤醒后台
    → 释放锁等待这一代发布，醒来重查
    → 返回
```

等待第一代时第二代活跃数据仍保留；不能只等已有 frozen 就返回。空活跃表不轮换，空数据库或重复空 flush 不生成 SSTable，不推进 Manifest revision。每条记录编码至少 9 字节，因此 activeBytes=0 可以判断空表。

flush 与写入背压共用 awaitFlushProgress，使用 Condition.await 原子释放锁并重新取得锁，之后检查 FAILED 或关闭状态。后台失败在等待调用中抛带原始原因的 IOException；已失败或关闭实例上的新 flush 调用由生命周期检查拒绝。轮换本身失败沿用已有错误处理并保留恢复来源。

中断只终止本次等待，恢复中断标志并抛 InterruptedIOException，不取消已有后台任务、不清除 frozen。调用结束后可以由后续串行调用查询或再次 flush；使用测试线程承接中断以便检查标志，并在调用结束后交回前台。

flush 等待的是发布完成，无须等待旧 WAL 的删除收尾。发布后其引用已经移除，旧文件删除失败不改变 flush 的数据语义。close 则需要等待工作线程退出后释放资源，因此二者的等待条件不同。

成功 put/delete 已依赖同步 WAL 保留恢复来源；显式 flush 进一步把内存数据发布为 SSTable，并使对应旧 WAL 可以回收。它不承诺阶段范围外的目录项断电持久性或并发前台快照语义。

## 验证

新增 LsmBackgroundFlushTest 的 20 个用例，全项目 `./mvnw test` 共 501 个通过。使用 CountDownLatch 固定后台构建和前台条件等待边界，不以 sleep 猜测调度，覆盖：

- 后台暂停时仍可写；满表后等待，等待操作尚未追加 WAL，发布后继续。
- 多代刷盘仅一个工作线程、一个同时构建任务；同键值与 Tombstone 在发布前后及重启后保持语义。
- 单条超目标、非法阈值、等待中断、轮换新建/封存/提交前后失败。
- 完整输出后失败、打开失败、发布前后失败，以及旧日志删除失败。
- 后台失败唤醒等待者、线程启动失败资源释放、关闭等待后台且保留中断标志。

显式 flush 小步新增 LsmExplicitFlushTest 的 12 个用例，全项目 `./mvnw test` 共 513 个通过。覆盖低于目标主动刷盘、空/重复 flush、同键覆盖与删除重开、两代分别暂停、仅有冻结代、两个等待位置中断、两代构建/发布失败、主动轮换失败及关闭后拒绝调用。

原目录恢复测试中需要观察冻结状态的场景也通过 latch 暂停后台，并在关闭前释放它，避免把线程调度偶然性写进断言。当前测试是方法级故障注入与重开，不等于数据库独立进程崩溃或断电实验；组合进程退出仍在后续验收任务中。
