# 最小 LSM 阶段复盘

本阶段把 MemTable、WAL、SSTable 组合为可重启恢复的目录级 LsmStore。前台串行调用，内部一个后台线程，最多一个活跃表和一个冻结表；支持 put、delete、get、flush 和 close。

## 两次提交把恢复来源连起来

假设初始 active 是 `1.wal`，没有 SSTable：

```text
写入：同步 1.wal → 更新 active MemTable → 返回成功

轮换：创建并同步 2.wal → 封存 1.wal
      → Manifest 提交 active=2、frozen=1、封存长度
      → 切换内存代，之后新写入使用 2.wal

发布：后台从 frozen 构建并同步 3.sst → 成功打开 Reader
      → Manifest 提交 active=2、无 frozen、SSTable=[3]
      → 安装 Reader、移除冻结表、唤醒等待者
      → 尝试删除 1.wal
```

轮换提交保证旧数据尚未发布时，两份 WAL 都有恢复身份；发布提交把 frozen WAL 的恢复职责交给完整 SSTable。文件存在不等于已经发布，只有最新有效 Manifest 决定读取哪些文件以及 SSTable 的新旧顺序。

冻结 WAL 的长度是封存时的确切字节数。仅有逐条 CRC 无法发现“恰好截掉末尾一整条记录”，长度检查可以发现这种情况。active 可能追加到一半退出，按合法残尾规则恢复；frozen 已停止写入，必须完整符合封存长度，不能截尾后假装成功。

## 读写、等待和关闭的不变量

| 边界 | 当前行为与理由 |
| --- | --- |
| 写入成功 | WAL 完整追加并同步后才更新内存、返回成功；未收到成功的操作也可能已进入有效日志 |
| 查询新旧 | active → frozen → SSTable 从新到旧；Value 和 Tombstone 都停止查找，仅缺失继续 |
| 刷盘期间 | frozen 不再修改，后台在状态锁外构建文件；前台仍可写未满的 active |
| 写入背压 | frozen 槽位忙且 active 已满时，下一条写入在追加 WAL 前等待，避免第三代内存表 |
| 显式 flush | 先等待 frozen，再轮换并等待非空 active；返回表示全部调用前数据已发布，无须等旧 WAL 删除 |
| 关闭 | 拒绝新操作，在锁外等待 worker 结束，再关闭共享资源；剩余 active 不强刷，由 WAL 恢复 |
| 后台失败 | 保存原因、停止服务并唤醒等待者；保留可能仍有效的文件，重启按磁盘有效状态恢复 |
| 无引用文件 | 完成引用打开和 WAL 重放后、启动 worker 前尽力清理；删除失败不撤销已恢复状态 |

例如旧 SSTable 保存 `k=A`、frozen 保存删除标记、active 保存 `k=B`，发布前后均返回 B；active 没有 k 时则返回 Tombstone。当前刷盘保留 Tombstone，直接丢掉它会让旧 SSTable 的 A 重新出现。

## 方案取舍

用户选择后台刷盘，让构建 SSTable 的耗时与前台写入重叠；只保留一个冻结槽位，代价是磁盘跟不上时写入等待。状态锁保护轮换和发布等共享状态，文件构建放在锁外，条件等待释放锁供后台完成发布。

默认每张内存表目标 4 MiB，统计每个键最新记录的编码字节总和。它是软目标：允许一条合法大记录越过目标，不等于堆内存、WAL 累计历史或 SSTable 文件大小上限。快照引用、索引和编码缓冲仍有额外内存开销。

Manifest 采用单文件追加完整状态快照，便于解释每次提交和恢复；代价是每次复制文件列表、历史持续增长。阶段 4 结束时尚无压缩或 Manifest 历史回收，SSTable 数量和点查成本会随刷盘增加，达到元信息容量上限时明确失败并保留恢复来源。

## 已有讨论与用户反馈

- 用户询问为何不采用后台刷盘，讨论后指示“就这样设计”；本阶段按已确定的单活跃表、单冻结表、单工作线程方案实现。
- 用户将 Manifest 理解为记录当前 WAL、冻结 WAL 和 SST、用于恢复；本阶段补全了轮换与 SSTable 发布两次提交，轮换时也必须记录文件集变化。
- 用户询问为何冻结表不变仍需加锁，以及“检查槽位”的含义；实现中锁协调共享槽位、Manifest、Reader 和生命周期，冻结表内容本身停止修改，耗时构建在锁外。
- 完成 flush、孤儿清理和独立进程验证后，用户继续指示推进；本次整理复盘、同步已实现规范并完成阶段归档，不扩展后续阶段。

## 验证与范围

`./mvnw test` 和 `./mvnw clean verify` 均通过 527 个测试，包括 6 个独立 JVM 退出恢复用例。测试覆盖两代数据的覆盖与删除、轮换和发布前后退出、真实 Writer 半成品、背压、等待中断、后台失败唤醒、关闭协调和恢复后续写。详细退出位置与证据见[进程恢复笔记](lsm-process-recovery.md)。

持久性范围是操作系统仍运行时的进程退出恢复，依赖平台文件同步语义；没有父目录同步协议，不承诺断电一致性。调用方必须独占目录，前台 API 串行调用。

后续阶段 5 已完成[压缩实现与复盘](compaction-review.md)：全部已发布表归并为单输出，保留 Tombstone，并通过文件集提交替换输入文件；自动阈值与同步手动请求共用唯一后台线程。
