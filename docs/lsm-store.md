# 目录恢复与基础 LSM 读写

本篇记录 LsmStore.open/get/put/delete/close 的基础读写与目录恢复。后续已接入日志轮换、阈值背压和一个后台线程，见 [后台刷盘笔记](lsm-background-flush.md)；显式 flush 尚待实现。

## 打开数据库的数据流

```text
确认给定目录已存在
  ├─ 空目录：新建 1.wal 并同步头 → 新建并同步初始 MANIFEST
  └─ 已有 MANIFEST：恢复有效文件集
         → 检查全部引用路径存在且是普通文件
         → 扫描保留命名空间中的最大编号
         → 按清单打开 SSTable
         → 只读严格重放 frozen WAL 到独立表（若有）
         → 恢复 active WAL 到另一张表，允许合法残尾修复
         → 全部成功后返回 LsmStore
```

不存在的目录不自动创建。没有 MANIFEST 的非空目录不自动初始化；已有零字节、残缺或非法 Manifest 沿用文件层失败规则。初始化先写 WAL 再写 Manifest，任何一步失败都释放资源并保留文件，不删除或覆盖后猜测初始化是否完成。

本步规范化文件名为正十进制编号、不补零，例如 `1.wal`、`3.sst`，Manifest 固定为 `MANIFEST`。历史讲解中的 001 只是编号示意。编号只控制身份与防覆盖，读取版本顺序仍取自 Manifest。

对最新状态引用的每个路径先检查存在和普通文件类型，不将目录或符号链接作为内部数据文件打开；未知文件保持原样。Manifest 自己可能已按其规则修复残尾，但在引用检查失败时不会补建 WAL，也不会修复活跃 WAL。历史中已经失效的引用文件不必保留。

## 两代 WAL 的恢复规则

原有 WalWriter.openRecovering 能打开不存在或零字节日志，这适合独立 WalStore 初始化，却不能用于数据库已经引用的文件：如果引用 WAL 丢失，补一个空日志会掩盖数据丢失。

因此新增两个用途明确的 WAL 入口，共享原有扫描与校验逻辑：

| 入口 | 文件打开方式 | 文件头与尾部 |
| --- | --- | --- |
| openExistingRecovering | READ + WRITE，不带 CREATE | 必须已有完整文件头；合法残尾可修复并同步 |
| replaySealed | READ | 实际长度必须等于封存长度；帧必须全部完整，不写、不截断、不同步 |

旧 openEmpty/openRecovering 的初始化与修复行为保持不变。

冻结日志在轮换前已经完整同步且停止写入，因此不允许有“正常残尾”。封存长度还能发现恰好截掉整条记录的情况；即使尺寸匹配，CRC、版本、字段和记录完整性仍须验证。回调只应用到未暴露的临时内存表，后面出现损坏或关闭错误时，整次打开失败，不返回部分恢复状态。

活跃日志则可能在最后一次追加中断，继续沿用 WAL 的残尾修复规则。恢复顺序先处理 SSTable 元信息和冻结日志，再处理活跃日志，避免冻结数据已知损坏时仍修改活跃日志。

## 查询顺序与删除遮蔽

```text
活跃 MemTable → 冻结 MemTable → 最新 SSTable → 更旧 SSTable
```

每层遇到 Value 或 Tombstone 都立即返回，仅缺失才继续。例如旧文件里 `k=A`、冻结表里 `k=Tombstone`、活跃表里 `k=B`，查询返回 B；活跃表没有 k 时返回 Tombstone，不能继续返回 A。

SSTable 打开仍仅验证元信息，访问候选块时完整验证。未访问块的损坏可能尚未被发现；查询遇到 I/O/格式错误时整个 LsmStore 进入 FAILED，不跳过文件查旧值。当前没有数据库级 scan，多文件按键归并不在本步实现。

## 写入与逻辑大小

put/delete 先检查参数及记录大小，然后完整追加并同步活跃 WAL，成功后才应用到活跃表。冻结表不接受修改。若 I/O 或内存应用失败，实例停止服务，只能关闭；完整日志记录可能在恢复后出现，失败不承诺回滚。

每张内存表独立计算最新映射的编码字节量：`9 + keyLength + valueLength`，不含 WAL 的 8 字节帧前缀；Tombstone 的 valueLength 为零。覆盖时先减旧记录再加新记录，删除保留一个有大小的记录，重放也使用相同规则。例如一个字节键和值的记录占 11 字节，改成删除标记后占 10 字节，多次覆盖的日志历史不累计到这个值。

大小使用 long、检查加法溢出，单条记录上限为 16 MiB。通过包内 activeBytes/frozenBytes 验证统计，不把它宣传成 Java 堆内存占用。后续 [后台刷盘](lsm-background-flush.md) 已按此统计接入正的可配置目标，默认 4 MiB。

## 文件编号与资源所有权

编号分配的起点同时考虑最新状态中的有效引用，以及目录里符合 `[1-9][0-9]*\.(wal|sst)` 的现有名称。未发布的高编号文件即使内容损坏也不参与恢复，但仍占用编号，避免未来覆盖。Long.MAX_VALUE 后分配报错，不回绕；超出 long 范围的保留名称使打开明确失败。非规范名称和其他文件均保留，本步不做孤儿清理。

allocateFileId 只是包内预留编号，不直接创建文件。新建初始 WAL 使用独占创建，Manifest 用 CREATE_NEW；后续轮换/刷盘也必须保持新建约束。

组合层的包内 FileOps 协调已有组件及工作线程，工厂返回成功后资源所有权才转给 LsmStore。打开失败逆序关闭已经取得的全部资源；一个关闭失败也继续关闭其他资源，主错误优先，清理错误 suppressed。后续 close 已增加 CLOSING 和锁外等待后台结束，之后才关闭文件；不强刷剩余活跃表，重启依赖其 WAL。

## 验证与下一步

本步新增 43 个用例（组合入口 29、WAL 严格恢复 14），全项目 `./mvnw test` 共 481 个通过。覆盖空目录初始化、二进制/空键空值、三态重开、两代表与多 SSTable 的同键遮蔽、逻辑字节覆盖统计、引用缺失/类型错误、初始化残缺、冻结日志逐字节及整条记录截断、活跃残尾修复、孤儿编号、损坏文件、打开失败资源释放及写入结果不确定。

本篇目录恢复用例中的文件集由夹具显式构建；后续新增的 [后台刷盘测试](lsm-background-flush.md) 已验证 LsmStore 自己生成文件并发布、回收旧 WAL，以及恢复冻结代后重新刷盘。显式 flush、启动时的孤儿清理和组合进程退出验收仍待完成。
