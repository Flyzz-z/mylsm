# SSTable 第四步：打开与三态点查

本步实现 `SsTableReader.open(Path)`、`get(ByteKey)` 和 `close()`。配合 Writer，可以写出文件后重新打开并点查；scan 尚未实现，WalStore 也尚未接入 SSTable。

## 打开只加载元信息

```text
只读打开文件 → 获取 fileSize → 验证最小长度
    → 读取 Header
    → 从 fileSize - 24 读取 Footer
    → 按 Footer 的位置和长度读取完整索引
    → 验证布局与索引键顺序 → 返回 Reader
```

只使用 FileChannel 的 READ 选项，不创建、修复或修改文件。打开期间先验证 Footer 给出的长度上限和文件范围，再分配索引数组，避免未经检查的文件字段控制内存分配。

索引解码为不可修改的对象列表，maxKey 为不可变 ByteKey，沿用已确定的简单表示。数据块在打开时不读取。因此 open 成功意味着元信息完整合法，不能解释为整个文件已经过检查。

打开失败会尝试关闭文件，关闭错误以 suppressed 保留，不返回半初始化对象。调用方须保证使用期间文件不被其他实例修改。

## 点查如何定位一个候选块

索引保存每块最大键。假设最大键依次是 c、g、m，查询 h 时，二分找到第一个 maxKey >= h 的项，即 m 对应的块。索引项提供文件 offset 与完整 frameLength，再从该区域读取数据。

```text
索引二分 → 读取整个候选块 → 完整验证 → 顺序查找目标键
```

如果键大于所有 maxKey，或文件是空表，则没有候选块，可以直接返回缺失，不读取数据区。如果定位到了候选块，还必须检查块内容，不能根据候选存在就认为键存在。块内或块间的键空隙都会正常返回缺失。

索引列表可按下标随机访问，变长键不妨碍内存二分。比较使用 ByteKey 的无符号字节字典序，保留空键、共同前缀和高位字节语义。

## 为什么先验证整块

数据块 Codec 检查帧声明长度与索引给出的实际字节数一致、CRC、记录数量与结构，以及块内严格顺序。Reader 随后交叉检查：

- 块内最后一键恰好等于当前索引 maxKey。
- 除第一块外，块内第一键必须大于上一项的 maxKey。

目标键即使出现在第一条记录，也要等上述检查全部完成才返回。否则可能把后半块的损坏或跨块边界矛盾当作合法文件中的正常结果。

当前没有数据块缓存，每次点查都会重新读取和解码候选块。索引二分约需对数次键比较，块内解码及查找与该块记录数量有关；不把这个实现视为已经优化过的性能方案。

## 保留三种查询结果

```text
Optional.of(Value)      找到字节值，包括空值
Optional.of(Tombstone)  找到删除标记
Optional.empty()       这个文件没有该键
```

删除标记不能转换为缺失：将来查询多个文件时，它需要阻止继续读到旧值。当前 Reader 只解释单个文件，文件之间的新旧顺序尚未实现。

测试通过公开 API 组合了 `MemTable.snapshot()`、记录类型转换、Writer 与 Reader，验证覆盖后的最新值和删除标记可以落盘再读出；这仍是显式组件组合，不代表自动冻结、文件集发布或 WAL 回收已经完成。

## 按需校验的边界

一个未访问的数据块损坏时，元信息可能仍然合法，open 和其他块的点查可以成功。查询大于全表最大键时也不会顺便检查无关块。

只有访问到坏块才报告错误；它不能作为“缺失”处理。将来完整 scan 会逐块检查全表，但 CRC 和结构检查仍不构成防恶意修改的认证机制。

## 短读、错误状态与关闭

一次 FileChannel.read 不保证读满，因此按已读取字节推进 long 偏移循环读取。读到提前 EOF 或返回 0 时抛 IOException，不把底层异常解释为正常缺失。格式验证也通过 IOException 报错。

生命周期为：

```text
OPEN → 文件/格式错误 → FAILED → close → CLOSED
OPEN → close → CLOSED
```

FAILED 不再查询，即使其他块可能仍然可读；这个策略让已知异常实例的行为清晰。它仍持有资源直到 close，调用方应使用 try-with-resources。null 键属于调用参数错误，不改变 OPEN 状态。

close 先将状态改为 CLOSED，再关闭底层文件。即使关闭报错，后续也不能查询，重复 close 不重复释放。
