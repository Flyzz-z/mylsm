# SSTable 第五步：有序遍历

`SsTableReader` 现在增加 `scan(Consumer<SsTableRecord>)`，完整接口为 open、get、scan、close。scan 按键顺序同步产生所有记录，包含 Tombstone，不提供范围或提前停止接口。

```java
try (var reader = SsTableReader.open(path)) {
    reader.scan(record -> {
        // 使用 record.key() 和 record.entry() 处理一条已验证的记录。
    });
}
```

## 一次读取并验证一个块

```text
索引项 0 → 读取并验证块 0 → 对块 0 的每条记录调用回调
索引项 1 → 读取并验证块 1 → 对块 1 的每条记录调用回调
……
```

遍历复用点查的 readBlock：检查帧长度、CRC、记录结构、块内排序、实际最大键与索引相等，以及首键大于上一索引最大键。只有整个块通过，才向回调产生这个块的第一条记录。

因此，块内第一条即使合法，后面的记录损坏也会让整个块拒绝输出。元信息中的块最大键递增，并且每块首键大于前一块最大键，所以按索引顺序遍历可得到全表严格递增顺序。

Reader 不预先读取后续数据块，不先把全表放进 List。索引仍完整保存在内存，数据按块缓冲；回调若自行保存全部记录，仍会占用全表内存。

空表没有数据块，scan 不执行回调，也不读取数据区。重复 scan 会重新读取全部块，当前没有数据块缓存。

## 文件错误与回调错误分开处理

假设三个块中第二块损坏：

```text
块 0 合法：回调已经收到其中的记录
块 1 损坏：不产生该块的任何记录，抛 IOException
块 2：不再读取
```

这不是“扫描失败等于从未发生”。前面回调可能已经改变了外部状态，Reader 不回滚这些副作用。Reader 本身进入 FAILED，之后只能关闭。

回调自身也可能失败，例如处理第一条记录时抛出 IllegalArgumentException。这表明调用方处理失败，不能据此认定文件损坏。异常原样向上传播，scan 停止，Reader 保持 OPEN，之后仍可 get 或重新 scan。回调抛 Error 时也不将其改写为文件错误；原异常传播，本次扫描 context 通过 try-with-resources 关闭。

实现上，在游标读块和点查读取时捕获 IOException 并将 Reader 标为 FAILED，consumer.accept 放在这个 catch 范围之外。这种异常边界比“把整个 scan 包进一个 catch”更准确。

## 独立 context 下的回调

当前 scan 为每次调用创建独立 Cursor，Reader 不再有全局 scanning 标志。每次 next/record 在共享生命周期读锁内完成，用户回调执行时已释放锁，因此可以点查、创建游标或启动嵌套扫描，各自位置互不影响。

回调或其他线程关闭 Reader 时可以完成关闭，本次扫描下一次读取明确拒绝，不发生锁升级死锁；回调仍不得修改正在读取的文件。回调自身异常只释放自己的 context，已有合法回调副作用不回滚。详见[独立读 context](sstable-read-context.md)。

## scan 与 get 的校验范围

| 操作 | 检查范围 |
| --- | --- |
| open | Header、Footer、整份索引 |
| get | 元信息加本次候选块；没有候选块时不读数据 |
| 完整 scan | 元信息加全部数据块和块间键边界 |

完整 scan 可以用于检查全表的当前格式不变量。若回调提前抛错，或前面块就损坏，后面的块不会读取，不能称为已完成全文件检查。CRC 也不构成对恶意修改的认证。

## 阶段复盘与讨论记录

严格递增且唯一的键是块最大键索引可以二分的前提。Writer 拒绝重复或逆序输入，Reader 在访问块时交叉验证实际键与索引边界；文件构建后只读，使这些边界在后续读取中保持稳定。索引定位只选出候选块，仍须验证整块后才能返回查询结果。

Value、Tombstone 与缺失是三种不同状态。删除标记仍保留统一记录头中的 valueLength，且要求为零；空 Value 同样可以长为零，靠 kind 区分。当前单文件 Reader 不把 Tombstone 转成缺失，为后续跨文件读取保留遮蔽旧值的信息。

讨论中已澄清多种大小的含义：4 KiB 是数据块 payload 的分块目标，合法大记录独占块，不跨块拆分；16 MiB 是包含 9 字节头的单条编码记录上限；索引项 frameLength 表示完整数据帧长度，包含 8 字节帧前缀。数据与索引的载荷上限约束分配和单文件规模，不代表文件系统块大小。

用户对照 LevelDB/RocksDB 讨论过索引表示和变长记录定位，曾考虑保留编码字节与偏移表，随后明确撤回该优化，选择恢复简单方案。当前打开时完整加载并解析索引为不可修改的对象列表，对索引对象二分；块内完整解析校验后顺序查找。后续是否优化，应由测量到的内存或查询成本决定。

损坏检测按访问范围发生：open 检查元信息，get 检查候选块，完整 scan 检查全部数据块；都不把错误伪装成键缺失。scan 在块验证完成后才回调，坏块没有输出，之前合法块的回调副作用不回滚。当前回调接口适合顺序消费和检查全表；阶段 5 已增加[可暂停游标](sstable-cursor.md)，供后续多路归并使用。

用户也确认过当前组件与 MemTable 落盘的关系：Writer 可以消费有序快照对应的记录，但当前尚未把 WalStore、MemTable 和 SSTable 串成自动刷盘流程。完整写出、force 与 close 成功只是单文件构建成功；崩溃半成品的识别、文件集发布和旧 WAL 回收需要后续协议，不能仅凭目录中存在文件就认为它属于数据库。
