# SSTable 第三步：构建真实文件

本步新增公开入口 `SsTableWriter.write(Path, Iterable<SsTableRecord>)`，将已排序输入一次性写入新文件。父目录必须存在，输入可以为空，但必须按 ByteKey 的无符号字节字典序严格递增。后续点查见 [Reader 笔记](sstable-reader.md)，scan 尚未实现。

## 写入的数据流

```text
CREATE_NEW 创建文件
    ↓
写 Header
    ↓
逐条验证记录与全局顺序 → 累积当前块 → 写数据块并记录索引
    ↓
写剩余块 → 写索引 → 写 Footer
    ↓
force(true) → close → 成功返回
```

输入迭代器只获取一次，Writer 不先收集整张表。它保存当前块与每块一项的索引；内存仍随块数增长，也包含 Codec 的临时字节副本。当前实现会通过复制键值字节取得长度，随后 Codec 再复制编码，优先保持步骤简单，没有性能基准结论。

每条记录先验证 null、键顺序和记录大小。与前一个键的比较是全局约束，不能只依赖每个数据块内部的排序检查，否则可能让相邻块分别合法而全表顺序错误。

## 4 KiB 是怎样分块的

当前块 payload 从 4 字节 recordCount 起算。加入下一条记录会超过 4096 字节，且当前块非空时，先写出当前块，再把新记录加入新块。记录不跨块。

例如键各 1 字节、值各 2036 字节的两条记录：

```text
单条：9 字节头 + 1 字节键 + 2036 字节值 = 2046 字节
两条：4 字节计数 + 2 × 2046 = 4096 字节 payload
帧长：8 + 4096 = 4104 字节
```

如果第二条值多 1 字节，两条就会分到不同块。一条 10 KiB 的合法记录会独占一个超过目标的块。空输入不输出空数据块，最终文件为 44 字节。

输出块时记录其实际最大键、起点和完整帧长。Writer 同时累加索引载荷的 `16 + 最大键长度`，一旦超过 64 MiB 就报 IOException，避免一直积累索引到结束才发现无法编码。

## 一个真实文件的偏移

只写 `k → A` 时：

| 区域 | 起点 | 长度 | 终点（不包含） |
| --- | --- | --- | --- |
| Header | 0 | 8 | 8 |
| 数据块 | 8 | 23 | 31 |
| 索引 | 31 | 29 | 60 |
| Footer | 60 | 24 | 84 |

索引中仅一项：`maxKey=k, offset=8, frameLength=23`。Footer 记录 `indexOffset=31, indexLength=29`。测试把这个文件的所有字节与独立 CRC 算法得到的固定样例比较，并通过现有 Codec 检查文件中记录与索引的对应关系；这不是提前实现生产 Reader。

## 完整写出、同步和关闭各解决什么

FileChannel 一次 write 不保证消耗整个 ByteBuffer，因此 Writer 循环写入，按实际写出字节推进 long 偏移。返回 0 或负数时立即报 IOException，避免无限等待；追加前检查偏移求和不会溢出。

完整字节写完不等于已完成同步，所以只在 Footer 也写完后调用一次 force(true)。与 WAL 每次操作同步不同，SSTable 是一次性构建的文件，成功边界是整个文件同步并关闭。

try-with-resources 负责关闭。同步成功但关闭失败仍然返回失败，并尝试删除文件。文件存在、甚至可以解码，都不代表此次调用报告了成功。同步的持久性仍依赖底层实现，且这里没有同步父目录项，不宣称新建文件名具有断电持久性。

## 失败清理与资源所有权

| 失败位置 | 行为 |
| --- | --- |
| path 或 records 为 null | 创建前拒绝 |
| 创建失败，包括目标已存在 | 不进入删除分支，原目标保留 |
| 创建后发现无序、重复、null 记录或超限 | 尝试关闭并删除本次文件，保留参数异常 |
| 写入、同步或关闭失败 | 构建失败，尝试清理本次文件 |
| 关闭或删除也失败 | 原始异常优先，清理异常放入 suppressed |

CREATE_NEW 同时检查并创建，避免先判断文件不存在再覆盖的间隙。调用方还必须独占构建目标，不能在构建和清理之间用其他文件替换这个路径。

输入校验是逐条完成的，后面的坏输入可能在前面块已写出后才发现；一次性接口通过失败清理处理这个边界。输入迭代器抛异常或 Error 也走资源释放与清理路径。

普通异常能触发清理，进程突然退出则可能跳过所有清理代码，留下半成品。下一阶段的文件集发布协议才能解决如何识别、采用或清理这些遗留文件；本阶段不能仅凭目录里存在某个 SST 文件就把它视为已发布，也不能据此回收 WAL。

## 最小故障注入边界与验证

Writer 包内有两个边界：FileOps 提供 createNew/delete，WriteIo 提供按偏移 write、force、close。默认直接使用真实 FileChannel 和 Files，不为后续读取提前扩展接口。

测试全部使用 JUnit @TempDir。故障代理仍写真实文件，只在指定边界制造短写、无进展或异常。覆盖各文件区域写入失败、同步时文件已完整、关闭后再清理、主错误与 suppressed 顺序、已有空文件保护、迭代失败、跨块顺序、分块边界和索引超限。

本步 `./mvnw test` 通过：新增 31 个用例，当时全项目 312 个，无失败。后续 Reader 已实现打开元信息、定位候选块并提供三态点查，见 [第四步](sstable-reader.md)。
